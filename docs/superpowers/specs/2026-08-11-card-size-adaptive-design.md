# 卡片尺寸自适应设计

> 2026-08-11 · 改的是卡片编排的核心契约，比一般改动更该留档
> 前置：[2026-08-10 卡片编排设计](./2026-08-10-card-orchestration-design.md)

## 为什么改

现在每个模板用 `sizes: string[]` 声明自己支持哪几种尺寸，是个白名单。白名单越窄，
桌面上的几何死角越多——**同一天栽了两次**：

1. 把确认卡的 `1/6` 砍掉（理由是"缩到那么小选项就看不见"，纯属想象）。导航卡 2/3
   占掉左两列后右列只有 1 格宽，横向的 1/3 塞不进去，于是导航中用户听到"你说第几个"，
   屏幕上什么都没有。
2. 给列表卡设 `minSize: '1/3'`（同样的想象）。导航中用户说"换成太古里"，Agent 念了
   四个候选让他选，候选卡整个被拒。

两次都是实测才知道 1/6 在 2560 屏上有约 800×460，放得下四个带地址的候选。

第二个动因来自真实使用：用户说「地图小一点」。导航卡只声明了 `2/3`，这个诉求在
真车机上非常自然，我们却只能回"做不到"——Demo 现场最尴尬的时刻。

## 契约变更

```ts
export interface CardTemplate {
  id: string
  label: string
  desc: string
  /** 首次出现时用哪个尺寸 */
  defaultSize: Size
  /** 可选：收窄可用尺寸。不写就是通用池 1/6 · 1/3 · 1/2 */
  sizes?: Size[]
  fields?: Record<string, FieldSpec>
}
```

- **通用池 = `1/6` · `1/3` · `1/2`**。不声明 `sizes` 的模板这三档全支持。
- `defaultSize` 只在**卡片首次出现**时生效。

### 两档不进通用池

**`full` 不是尺寸，是覆盖层。** 它整屏覆盖、不占栅格、退出自动还原。任意卡都能 full
意味着天气卡能盖住导航——行车中这是安全问题。只有明确需要独占的模板才在 `sizes` 里
写上它（目前只有能力目录）。

**`2/3` 是稀缺档。** 2×2 方块、左锚定、全桌面只有一个合法位置——两张 2/3 必然冲突。
只留给需要大画布的卡（目前只有导航）。所以导航默认 2/3、可以被调小到 1/2 或 1/3，
但别的卡升不到 2/3。

各模板：

| 模板 | defaultSize | sizes | 说明 |
|---|---|---|---|
| nav | `2/3` | `1/3` `1/2` `2/3` | 唯一能用 2/3 的 |
| capability | `full` | `1/6` `1/3` `1/2` `full` | 唯一能用 full 的 |
| weather | `1/6` | — | 通用池 |
| control | `1/6` | — | 通用池 |
| confirm | `1/3` | — | 通用池 |
| list | `1/2` | — | 通用池 |
| feedback | `1/6` | — | 通用池 |
| notice | `1/6` | — | 通用池 |
| info | `1/6` | — | 通用池 |
| media | `1/3` | — | 通用池 |
| generic | `1/3` | — | 通用池 |

## 尺寸粘性（方案能不能用的前提）

桌面是 `f(车辆状态)`：导航中每次 ETA、剩余距离、下一步指令变化，orchestrator 都会
重刷导航卡。如果刷新时带着 `defaultSize`，**用户说"地图小一点"调到 1/3，下一秒 ETA
一跳就弹回 2/3**。用户会觉得它不听话。

规则：

- 卡片记一个 `sizeLocked` 标记，`card.resize` 成功后置为 true
- `render()` 遇到已存在的卡：`sizeLocked` 为 true 时**只更新数据，不碰尺寸**
- 卡片退场后标记随之消失，下次出现回到 `defaultSize`
- 仲裁（空间不够时的自动缩放）不受此限——那是几何约束，不是偏好

用一句话说清区别：**默认值是系统的建议，显式设定是用户的意愿，仲裁是物理现实。**
优先级 物理 > 意愿 > 建议。

## 每个模板的最小形态

"支持某个尺寸"要落到"在那个尺寸下能看"。缩到最小时保留什么：

- **导航卡 1/3**：转向条 + ETA + 目的地，**不显示地图**。这就是真车机的小卡模式。
  1/2 时显示地图但压扁。
- **能力目录 1/6**：只报"共 N 项能力"，提示放大看
- **天气 1/2**：现在的竖排 rowline 会拉得很空，改横向排布
- **列表 1/6**：已验证放得下四项
- **确认 1/6**：已验证放得下两个选项

### 活地图的副作用

导航卡的 AMap 实例绑在持久化的 `.mapbox` 节点上（不能跟着文字一起重绘，否则闪屏丢
视角）。尺寸变化时容器尺寸变了，必须处理：1/3 时销毁实例（那个尺寸不显示地图），
放大回来时重建。不处理会留下错位的画布。

## 分两步

**第一步（本次）**：机制。`defaultSize` + 尺寸粘性 + 全尺寸放开 + 每个模板一个能看的
最小形态。做完死锁消失，「地图小一点」可用且不弹回。

**第二步（后续）**：打磨每个模板在每个尺寸下的具体排版，对着截图一个个过。

## 影响面

- `src/config/cards.ts`：契约与 11 个模板的声明
- `src/tools/registry.ts`：`checkSize` 改成认通用池 + 模板收窄
- `src/cards/desk.ts`：`sizeLocked` 标记、render 复用时不碰锁定的尺寸
- `src/cards/orchestrator.ts`：规则刷新不传尺寸（首次除外）
- `src/screen/main.ts` + `screen.html`：各尺寸渲染形态
- `src/screen/mapView.ts`：尺寸变化时的实例生命周期

不影响：约束引擎、Tool 注册表机制、Agent 编排。

## 不做

- 不做"按内容多少自动选尺寸"——那是最优解，我们要的是可预测解
- 不做尺寸的过渡动画（栅格位置变化已经有 CSS transition，够了）
- 不把 `2/3` 和 `full` 放进通用池，理由见上
