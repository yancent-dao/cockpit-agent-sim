# 自动化闭环评审清单

每轮 pilot 跑批后，对着这份清单逐条判断。**不要笼统地说"感觉还行"**——每条都要能对着快照 JSON 或截图判 yes/no。

角色分工：用户机器人只负责说人话；判断（本清单）与修复由我（Claude）承担，扮演产品 + 开发。

---

## 1. 产品设计是否合理（该不该有这个东西）

- [ ] 这张卡是用户此刻真需要的，不是系统自嗨（反例：全关状态还弹「门与舱盖：全部关好」）
- [ ] 关键字段没缺（导航要有 ETA/剩余里程/下一步；天气要有当前温度与天况）
- [ ] 没有硬塞不该占位置的信息
- [ ] 卡片存在时长合理（车控反馈 30s？导航常驻？天气 120s？）
- [ ] 撤卡时机分清两类：**问题卡**（voice.ask）用户一开口就该撤；
      **候选/结果卡**不能这么撤——用户下一句常常正是冲着屏幕问的
      （"上面那个离这儿多远？"），撤了他就没东西可指，按"这件事翻篇"撤
- [ ] 同一意图没有产出重复表达（反例：候选列表卡 + voice.ask 问题卡两张同时在场）
- [ ] 能力边界诚实——做不到的事没有假装做到（CAR-bench 反幻觉红线）

## 2. 用户交互是否合理（用起来顺不顺）

- [ ] 一次意图的轮数合理，没有本可一步完成却问废话
- [ ] 消歧时机对：该问的时候问了，不该问的时候没瞎问
- [ ] 语音与屏幕分工清楚：话术补充屏上没有的，而不是复述屏上已有的
- [ ] 拒绝/失败时用户知道下一步该干什么（suggestion 起作用了）
- [ ] 多轮指代能接住（"再热一点""换个地方""算了"）
- [ ] 用户说完到看到结果的等待时间可接受（看 trace 的耗时）

## 3. 架构是否合理（代码有没有腐烂）

**自动检测项**（run.ts 里的确定性规则，不靠模型判断）：
- [ ] `navigation.active=true` 时桌面必有导航卡
- [ ] 同类选择卡不超过一张（nav-candidates 与 ask 不共存）
- [ ] 没有 Tool 返回 `DATA_SHAPE_MISMATCH` / `SIZE_NOT_SUPPORTED`（说明 Prompt 或规则没说清）
- [ ] 没有 `NO_HANDLER` / `HANDLER_ERROR`
- [ ] 话术里没有思考标签泄漏、Markdown 标记、底层模型身份、经纬度数字
- [ ] 话术没让用户"点一下"（车机屏不可交互，用户在开车）
- [ ] 话术没声称"屏幕上有…"而桌面其实是空的
- [ ] 话术不超过 100 字（语音播报念一百字要二十多秒）
- [ ] 等位区（2026-08-13）没有排太久的卡——排 ≥3 张只是提示，不是硬伤，
      但值得看一眼是不是场景本身桌面压力就大
- [ ] 屏上已有列表卡时，话术没有逐条复述数字
- [ ] 用户机器人没串戏演助手（串了这一轮的结论全部作废，先修跑批器再看产品）

**人工判断项**：
- [ ] 问题修在正确的层：规则层（cardRules）／机制层（desk、orchestrator）／Prompt 层（Tool desc）。修错层就是欠债
- [ ] 没有意图分支、关键词匹配、意图枚举（CLAUDE.md 硬约束）
- [ ] 新增能力只改 `src/config/*.ts`；动了 `src/core/` 说明抽象错了
- [ ] 布局可预测：同场景两次跑结果一致
- [ ] 行数预算：超了要判断是拆分还是抬预算，不能装没看见

## 4. 界面是否好看（对着截图看）

- [ ] 布局平衡：没有大片空白、没有挤成一坨、2/3 卡旁边不是孤零零一张小卡
- [ ] 文字不溢出、不截断、换行不难看；数字对齐
- [ ] 地图图片加载成功、比例正确、没有拉伸变形
- [ ] 视觉层级清晰：标题／主数据／次要信息权重分明
- [ ] 符合 Design Token（深浅色、圆角、间距），没有例外样式
