# 座舱 Agent 模拟环境 · 需求规格说明书 v1.0

**文档状态**：需求冻结候选 · 唯一事实来源
**取代**：v0.1 接口定义、v0.2 分层修正与UI设计、v0.3 无APP化卡片桌面需求（三份作废，仅保留《市场调研与设计对标》作为附录参考）
**日期**：2026-08-10

## 0. 摘要

### 0.1 要做什么

一套 Web 端的**座舱底层软件模拟环境**，为座舱 Agent 类 Demo 提供统一的车辆状态、能力接口、屏幕规范与演示控制，使每次做 Demo 不再从零开始、不再各行其是。

### 0.2 为什么值得做

- 从第 3 个 Demo 起，每个可省 60%~70% 重复工作
- 多个 Demo 共用底层后能拼成连贯的产品愿景，而非孤立的点
- **这套接口定义本身就是给研发的需求交付物**，不是 Demo 的附属品
- 对 Agent 座舱尤其关键：**Agent 的产品定义 = 它的 Tool 集合**，定义这套接口就是在定义产品

### 0.3 行业位置（详见附录 A）

截至 2026-08：

- 车控 tool calling 在头部主机厂已是标配，**不再是差异点**；竞争焦点已转向长期记忆、任务规划、多 Agent 协同、跨场景连续性
- **全球不存在任何一份公开的「车载 Agent 能力描述规范」**——这是真空，不是我们没找到
- 现成工具的分布：Kanzi/Qt/Unity 解决"HMI 长什么样"；RemotiveLabs+ProtoPie 解决"UI 接真实信号，但没有 Agent"；VehicleWorld/CAR-bench 有完整 Agent 工具语义但**是没有 UI 的 Python CLI**。**中间那块没有产品**
- 安全与授权机制是全行业公开空白（20+ 厂商中仅 Hyundai 公开命名 guardrail agent）——**我们把确认与拒绝做扎实是领先，不是补课**

### 0.4 核心设计原则（五条，贯穿全文）

| # | 原则 |
|---|---|
| 1 | **Tools = 机制，Agent = 策略。** Tool 内不写任何"贴心逻辑"，所有意图理解与编排归 Agent |
| 2 | **平台不认识任何具体 Agent。** Agent 通过 Manifest 注册，新增 Agent 不改平台一行代码 |
| 3 | **不发明命名，不发明协议。** 信号对齐 VSS，元数据对齐 AAOS，确认流对齐 MCP MRTR |
| 4 | **拒绝必须携带机器可读原因。** Agent 的话术质量直接取决于拒绝信息的质量 |
| 5 | **无APP化下，"该执行什么"与"该显示什么"是两类决策**，必须分开建模 |

### 0.5 启动方式

**寄生式演进**：模拟环境永远挂在一个真实 Demo 需求上演进，不允许独立立项。
**v0.1 验收标准不是"平台建好了"，而是"下一个 Demo 用它做出来了，且比不用更快"。**

## 1. 架构分层

```
┌───────────────────────────────────────────────────────────────┐
│ 应用层 · Agent 实例（可插拔，平台不认识它们）                     │
│   主Agent  │  导航Agent  │  儿童看护Agent  │  …（未来）           │
├───────────────────────────────────────────────────────────────┤
│ Agent Runtime（平台提供，通用，不含任何具体 Agent 逻辑）           │
│   Manifest 加载 · 能力授权 · 上下文注入 · LLM 适配                │
│   会话与多轮 · 并行编排 · 确认流(MRTR) · 调度仲裁 · 可观测         │
├───────────────────────────────────────────────────────────────┤
│ 能力层 Tools                                                   │
│   L1 系统级：车控 · 卡片调度 · 语音 · 感知                        │
│   L2 应用级：导航 · 媒体 · 通讯 · 信息 · 记忆                     │
├───────────────────────────────────────────────────────────────┤
│ 状态层 State Store                                             │
│   信号定义 · 约束联锁 · 过渡仿真 · 桌面布局状态                    │
└───────────────────────────────────────────────────────────────┘
```

### 1.1 L1 与 L2 的分界（产品意义大于技术意义）

| | L1 系统级 | L2 应用级 |
|---|---|---|
| 依赖 | 车自身硬件，一定存在 | App / 服务 / 网络 / 登录态 |
| 失败语义 | **车拒绝执行**（有物理或安全原因） | **服务不可用**（要有降级话术） |
| Agent 应对 | 解释原因 + 给替代方案 | 坦白 + 转移 |

> Agent 面对两种失败的对话策略完全不同。Demo 里把这个差别演出来很有说服力。

### 1.2 分层是否成立的唯一验收标准

> 新建一个只挂 3 个 Tool、20 行人设的 `demo-agent`，**不改平台任何一行代码**就能跑起来。
> 做不到，说明分层是假的。

### 1.3 Agent Manifest

Agent 对平台而言是一份声明 + 一段 Prompt，不是代码：

```yaml
id: main-agent
name: 主Agent
version: 1.0.0
persona:
  prompt: ./prompts/main-agent.md
  tone: neutral
capabilities:
  tools: ["*"]                      # 主Agent 全量；子 Agent 用白名单
activation:
  triggers: [wakeWord, textInput, systemEvent]
  wakeWord: ["你好小X"]
channels:
  voice:  { priority: 10, interruptible: true }
  screen: { zone: agentZone }
context:
  inject: [vehicleState, desktopLayout, environment, speakerPosition, userMemory]
runtime:
  thinkingMode: auto                # fast / slow / auto
handoff:
  canDelegateTo: []                 # v1.0 留空，接口先在
```

### 1.4 多 Agent 共存：v1.0 只留接口

| 问题 | v1.0 做法 |
|---|---|
| **谁来接**（路由） | 只有一个 Agent 直通，但 `route(input, agents) → agentId` 函数必须存在 |
| **谁在说**（通道仲裁） | 实现单占用者 VoiceChannel，接口按多方竞争设计 |
| **能用什么**（能力授权） | **必须现在实现**。权限检查拦在 Tool 执行前，后补会牵动所有调用路径 |

## 2. 状态层

### 2.1 命名规范

**双轨制：内部短别名用于 Prompt 注入（Token 效率），VSS 路径为必填字段（工程可交接）。**

```yaml
- alias:      cabin.window.driver.position          # lowerCamelCase，点分层级
  vssPath:    Vehicle.Cabin.Door.Row1.DriverSide.Window.Position   # 必填
  access:     READ_WRITE
  changeMode: ONCHANGE
  permission: 彩
  range:      [0, 100]
  transition: 4000        # ms，全行程耗时
```

**构建期硬校验：任何没有合法 `vssPath` 的信号不允许注册。**

> ⚠️ VSS v6.0（2026-01）含破坏性变更：移除 OBD 分支、座椅信号重构、单位 `celsius`→`Celsius`、部分 Left/Right 改为 DriverSide/PassengerSide。**本文给出的 vssPath 均为示例，冻结前必须逐条对照 VSS v6.0 官方 catalog 核验。**

**其它约定**

| 类别 | 规范 | 示例 |
|---|---|---|
| 位置枚举（全局唯一一套） | — | `driver` · `passenger` · `rearLeft` · `rearRight` · `all` |
| 枚举值 | lowerCamelCase | `faceFeet` · `onePedal` · `parkingGarage` |
| 错误码 | UPPER_SNAKE_CASE | `SPEED_TOO_HIGH` · `NOT_EQUIPPED` |
| 百分比 | 0–100 整数，0=全关 | `window.position` |
| 档位 | 0–N 整数，0=关 | `seat.heating: 0–3` |

### 2.2 信号元数据三元组（对齐 AAOS VehiclePropertyIds）

| 维度 | 取值 | 对 Agent 的意义 |
|---|---|---|
| **Access** | READ / WRITE / READ_WRITE | 决定是否生成 set 类 Tool |
| **ChangeMode** | STATIC / ONCHANGE / CONTINUOUS | **决定上下文注入策略**：CONTINUOUS（车速）只注入摘要不全量；STATIC 只注入一次 |
| **Permission** | 黑 / 灰 / 彩 | 见 §3.3 |

> ChangeMode 是最容易被漏掉、但直接决定 Prompt 构造策略的一维。

### 2.4 全量信号域（v0.2+ 逐步补齐）

行驶与动力 · 热管理 · 车身开闭件 · 座椅与个人化 · 灯光氛围 · 感知 · 环境 —— 共约 65 个信号。
**补齐时用 VehicleWorld（250 API）/ VehicleMemBench（111 API / 23 类）交叉校验，不从零推演。**

### 2.5 约束与联锁（v0.1 必做）

这些不是技术细节，是 **Demo 的戏剧张力来源**：

| 规则 | 条件 | 拒绝码 |
|---|---|---|
| 行驶中禁开门 | `speed > 5` 且请求开门 | `SPEED_TOO_HIGH` |
| 非 P 挡禁开后备箱 | `gear !== 'p'` | `GEAR_NOT_PARK` |
| 儿童锁联锁 | `childLock = true` 时后门/后窗不可控 | `CHILD_LOCK_ON` |
| 高速开窗限位 | `speed > 100` 时窗开度上限 30 | `SPEED_LIMITED` |
| 低电降功率 | `soc < 10` 时空调风量上限 3 | `LOW_BATTERY_LIMIT` |
| 配置缺失 | 该车型未选装 | `NOT_EQUIPPED` |
| 参数越界 | 超出定义范围 | `OUT_OF_RANGE` |

### 2.6 过渡仿真（轻量，不做总线级）

明确**不做** CAN 时延、信号丢失、报文级仿真。只做三件事即可让状态"像真车"：

1. **过渡时长**：车窗全行程 4s、天窗 6s、座椅 3s、温度每分钟变化 ≤3℃ → 中间态可见、可打断
2. **派生联动**：`range` 随 soc/空调负载/驾驶模式实时重算；`temperature.inside` 向 targetTemp 逼近
3. **时间轴**：`env.time` 支持 1× / 10× / 60× 加速与暂停

### 2.7 状态不变量断言（运行时持续校验）

违反即在调试面板报警，例如：
- `speed > 5` 时不存在 `door.*.isOpen = true`
- 所有 position ∈ [0, 100]
- `childLock = true` 时后窗 position 不发生变化

## 3. 能力层（Tools）

### 3.1 统一返回契约

```ts
type ToolResult =
  | { status:'ok';            data?:object; changed?:string[]; code?:string; message?:string }
  | { status:'rejected';      code:string; message:string; suggestion?:string }
  | { status:'inputRequired'; code:'CONFIRM_REQUIRED'; message:string; token:string }   // MCP MRTR
  | { status:'unavailable';   code:string; message:string; suggestion?:string }
  | { status:'failed';        code:string; message:string }
```

| status | 含义 | Agent 应对 |
|---|---|---|
| `rejected` | 车**能懂但不让做**（安全/物理约束） | 解释原因 + 给替代方案 |
| `unavailable` | 车**做不了**（未选装/App 未装/无网/未登录） | 坦白 + 转移（**这就是能力发现的失败转移，不是两套逻辑**） |
| `failed` | **执行出错**（含故障注入） | 致歉 + 建议重试 |
| `inputRequired` | 需二次确认 | 向用户确认后带 token 重调 |

**`message` 必须写成人话，不是日志**——它会直接进模型上下文。
✅ `"当前车速 62km/h，行驶中无法开启车门"`
❌ `"ERR: door_open denied by speed guard"`

### 3.2 二次确认流程（对齐 MCP 2026-07-28 MRTR）

```
1. Agent 调用  door.set({door:'trunk', action:'open'})
2. Runtime 拦截 → 返回 { status:'inputRequired', message:'即将打开后备箱，确认吗？', token:'ct_a8f3' }
3. Agent 用 voice.ask / 确认卡 向用户确认
4. 用户确认后，Agent 带 token 重新调用同一 Tool
5. Runtime 校验 token（60s 有效、一次性）后真正执行
```

**由 Runtime 拦截，不是靠 Agent 自觉。** 采用 MCP MRTR 的 `inputRequired` 形态而非自造字段，未来把 Tool 层暴露成 Cockpit MCP Server 时零改造（Qualcomm 官方架构已给出 Cockpit MCP Server 的位置）。

> 产品价值：这把"哪些事 AI 能自作主张"变成了**可配置参数**。评审现场把某个 Tool 从彩改成灰，体验差异立刻可见。

### 3.3 权限分级（对齐行业「黑/灰/彩」）

| 级别 | 含义 | 判据 | 示例 |
|---|---|---|---|
| **彩** | Agent 可直接执行 | 可逆、无安全影响 | 调温、切歌、氛围灯、卡片调度 |
| **灰** | 需二次确认 | 命中四判据之一：**不可逆 / 涉及安全 / 涉及金钱 / 涉及他人** | 开车门、行驶中开窗、支付、发消息、固定区入驻 |
| **黑** | **永久禁区**，永不开放给 Agent | 直接影响行车安全 | 刹车、转向、驻车释放 |

> ⚠️ 语义修正：「黑」= 永久禁区（Tool 根本不注册给 Agent）；`rejected` = 当前条件不满足（Tool 存在但本次拒绝）。这是两件事，早期版本混淆过。

## 4. 卡片桌面（无APP化）

### 4.1 前提与核心命题

无APP化改变了 Agent 的职责定义。有 App 的座舱里"显示什么"由 App 负责；无APP化把这份责任交还给 Agent。

> **Agent 面对两类决策：「该执行什么」和「该显示什么」。必须分开建模。**
> 执行对了但桌面一团糟，用户体感依然是失败。

### 4.2 栅格（已锁定）

主内容区 = **3 列 × 2 行 = 6 格**

| 尺寸 | 占格 | 形状 |
|---|---|---|
| `1/6` | 1 格 | 1×1 |
| `1/3` | 2 格 | **横向 1×2（唯一形状，无竖向）** |
| `1/2` | 3 格 | 整行 1×3 |
| `full` | 6 格 | 2×3 |

**每个尺寸只允许一种形状。** Agent 的布局问题从二维装箱降为一维排布，编排逻辑复杂度大幅下降。

### 4.3 分区（已锁定）

| 区 | 位置 | 归属 | 规则 |
|---|---|---|---|
| **固定区** | **下行 3 格** | 用户 | Agent 不可自行改动内容与位置 |
| **Agent 区** | **上行 3 格** | Agent | 可自由创建、替换、缩放、清理 |

**三条已锁定的规则：**

1. **固定区可被临时征用**：全屏卡、系统卡（来电/告警）可临时覆盖整屏，**退出后自动还原**
2. **固定区入驻需用户确认**：Agent 可建议（"要不要把充电卡固定到桌面？"），但 `desktop.pin` 为**灰**级
3. **Agent 区满载策略**：**降尺寸优先 → 降无可降再 LRU 挤出 → 并告知用户**
   （例："我把刚才的搜索结果收起来了"。静默消失是不可接受的）

### 4.4 卡片分类（按来源与生命周期）

| 类别 | 来源 | 生命周期 | 所在区 | 示例 |
|---|---|---|---|---|
| **常驻 Persistent** | 用户固定 | 长期，仅用户可移除 | 固定区 | 空调、媒体、导航、车况 |
| **任务 Task** | Agent 因一次意图生成 | 有 ttl 或任务结束即退 | Agent 区 | 搜索结果、确认、反馈、推荐 |
| **系统 System** | 系统事件 | 事件结束即退，**有抢占权** | 可覆盖任意区 | 来电、告警、充电完成、故障 |

### 4.5 卡片模板清单（模板为主 + 通用卡兜底）

| # | 模板 | 说明 | 支持尺寸 | P0 |
|---|---|---|---|---|
| 1 | **车控卡** | 通用：开关/滑条/分档三种控件自由组合。**车窗、空调、座椅、氛围灯共用这一张** | 1/6 · 1/3 | ✅ |
| 2 | 媒体卡 | 封面、曲目、进度、传输控制 | 1/6 · 1/3 · 1/2 | |
| 3 | 导航卡 | 目的地、ETA、剩余里程、下一路口 | 1/3 · 1/2 · full | |
| 4 | 列表卡 | 搜索结果、候选项、可选择 | 1/3 · 1/2 | |
| 5 | **确认卡** | 问句 + 选项按钮（配合 MRTR 确认流） | 1/6 · 1/3 | ✅ |
| 6 | **反馈卡** | 执行结果摘要，可带微调控件 | 1/6 | ✅ |
| 7 | **提示/拒绝卡** | 拒绝原因 + 替代方案 | 1/6 · 1/3 | ✅ |
| 8 | 信息卡 | 天气、车况、日程等只读信息 | 1/6 · 1/3 | |
| 9 | **能力目录卡** | 由 Tool Registry 自动生成 | full | ✅ |
| 10 | **通用卡（兜底）** | 标题+文本+列表+按钮+滑条 自由组装 | 全部 | ✅ |

> 第 1 和第 10 是关键：车控卡一张覆盖所有原子车控，通用卡保证 Agent 不会"没卡可用"。这两张做好，模板数量就不会失控。

### 4.6 卡片实例必填字段

| 字段 | 取值 | 说明 |
|---|---|---|
| `ttl` | `persistent` / `<秒>` / `untilTaskEnd` / `untilDismissed` | **必须显式指定，不允许省略** |
| `priority` | `system(4) > confirm(3) > task(2) > persistent(1)` | 抢占顺序 |
| `preemptable` | bool | 是否可被挤走 |
| `onPreempt` | `restore` / `shrink` / `drop` | 被挤走后的去向 |

Demo 里最容易翻车的就是卡片堆积，所以生命周期是硬要求。

### 4.7 交互深度分级

| 尺寸 | 交互能力 |
|---|---|
| `1/6` | 只读 + 最多 1 个主操作 |
| `1/3` | 完整控件，单层 |
| `1/2` | 完整控件 + 列表/二级内容 |
| `full` | 完整交互，可含分区与滚动 |

**点击卡片 = 逐级放大**（1/6 → 1/3 → 1/2），与 `card.resize` 形成用户侧对照。长按 = 固定/移除。

### 4.8 反馈体系（四级，替代早期三级方案）

| 级别 | 形式 | 触发条件 |
|---|---|---|
| **L1 卡内控件级** | 目标卡已在桌面 → 卡内控件动 + 高亮描边 2s | **默认路径** |
| **L2 卡片变形级** | 卡已在但尺寸不足 → 放大一级 | 需展示更多信息 |
| **L3 新建卡片级** | 桌面无对应卡 → 新建，按 ttl 退出 | 前两级不适用 |
| **L4 语音级** | TTS 播报 | 需解释时（拒绝、降级、主动提醒），与上三级叠加 |

**核心原则：优先复用桌面上已有的卡 → 其次放大 → 最后才新建。**

这既是防止卡片爆炸的工程规则，也是 Agent 编排能力的直接体现——做得好不好，观众一眼看得出。

**实现要求**：L1~L3 全部由 `state.changed` 与卡片调度事件自动驱动，Agent 不需要为基础反馈额外调 Tool。

## 5. Agent Runtime

### 5.1 主 Agent 在 v1.0 的定位

**测试探针，不是产品。** 人设 ≤ 20 行，无长期记忆、无情感、无主动式（v0.2 再加）。

它的价值是证明 `State → Tool → Runtime → UI` 这条链路在真实模型调用下是对的。

> 判断底层好坏的标准不是"Agent 表现好"，而是**"Agent 表现差的时候，能一眼看出是模型的问题还是底层的问题"**——这靠可观测面板保证。

### 5.2 上下文注入（每轮）

```
[System Prompt]
├─ 角色与人设
├─ 能力边界声明（能做什么 / 明确不能做什么）
├─【动态】车辆状态快照        ~20 行，按 ChangeMode 裁剪（CONTINUOUS 只给摘要）
├─【动态】桌面布局摘要        ~5 行，当前卡片与剩余容量        ← 无APP化新增
├─【动态】环境快照            时间、天气、位置、路况
├─【动态】说话人位置          来自 perception.voiceSource，用于指代消解
├─【动态】用户偏好            来自 memory（v0.2）
└─ 输出规范与拒绝话术原则
```

状态直接注入而非让 Agent 调 `getState`，是为了省掉一轮往返——座舱对首响延迟敏感。

### 5.3 执行循环

```
用户输入 / 主动事件
   ↓
主 Agent 推理（流式话术与工具执行并行）
   ↓
并行 Tool 调用 → 能力授权检查 → 约束校验 → 执行
   ↓                  ↓ inputRequired        ↓ rejected
   ↓              向用户确认 → 带 token 重调   Agent 组织解释话术
   ↓
状态/卡片变更事件 → UI 四级反馈自动驱动
   ↓
可观测面板记录全链路
```

### 5.4 thinkingMode（对齐行业快慢思考范式）

| 模式 | 场景 | UI |
|---|---|---|
| `fast` | 明确指令直通，跳过深度推理（"开窗"） | 无 thinking 态或极短 |
| `slow` | 开放性问题走完整推理 | 显示 `thinking` 状态 |

v1.0 不实现两套模型，但**接口与 UI 状态必须留出**——语音形象状态机里的 `thinking` 正好对应。

### 5.5 可观测面板（P0）

一屏展示：`用户输入 → 注入的状态摘要 → 模型推理 → Tool 调用(名称/参数/权限级) → 返回结果 → 卡片变化 → 最终话术 → 各段耗时`

> 建议做成可投屏的独立窗口。评审时左边座舱界面、右边这个面板，**"AI 到底做了什么"的黑盒感会消失**——这是说服技术和管理层最有效的方式，且目前未见任何厂商公开做过。

### 5.6 主动式触发（v0.2）

规则引擎监听状态变化，以 system event 唤起 Agent（不硬编码话术，让模型自己组织）：
低电且目的地不可达 · 疲劳持续 30s · 距目的地 <2km 且为家 · 天气转雨 · 主驾就座且 P 挡 · 熄火后儿童遗留。

分级参考行业做法（长城「相识 → 相知 → 相助」）。

## 6. 能力发现（无APP化最大的产品风险）

**双轨制：能力目录入口 + Agent 主动引导。**

### 6.1 能力目录卡

**硬性要求：由 Tool Registry 自动生成，不允许手写页面。**

1. 能力增减自动同步，不会出现"目录里有但实际没有"
2. 未选装能力自动置灰，可直观展示车型配置差异
3. **这份目录页 = 给研发的接口文档**，一份内容两处用

### 6.2 Agent 主动引导的三个时机

| 时机 | 说明 |
|---|---|
| **失败转移** | 能力不可用时给替代方案。**这与 `unavailable` 的拒绝话术是同一件事，不是两套逻辑** |
| **对话顺带** | 任务完成后一句附加提示。需设频次上限，避免话痨 |
| **场景触发** | 首次进入某场景时提示相关能力（第一次下雨时提示自动关窗） |

### 6.3 能力曝光度（v0.2）

记录每个 Tool 的调用次数，**从未被使用的能力优先进入主动引导队列**。

Demo 里可做成可视化——「这台车有 44 项能力，用户实际用过 9 项」——把"无APP化会不会让能力沉默"这个抽象担忧变成可量化的东西。

## 7. 界面与交互规范

### 7.1 双界面架构（已实现验证）

| 界面 | 用途 | 内容 |
|---|---|---|
| **车机屏** | 投屏演示，纯净无调试元素 | 状态栏 + 卡片桌面 + 语音层 |
| **控制面板** | 演示者操作，独立窗口 | 状态调节、场景预设、Golden Case、语音形象状态、全链路日志 |

两者通过 postMessage + BroadcastChannel 双通道同步。

### 7.2 画布规范

| 项 | 取值 |
|---|---|
| 基准屏 | 中控 15.6"，**2560 × 1440**（16:9），设计稿 1:1 对应 CSS 像素 |
| 缩放 | `transform: scale(min(vw/2560, vh/1440))`，整屏等比 |
| 安全区 | 上下 40px，左右 60px |
| 状态栏 / 语音层 | 96px / 300px |
| 主内容区 | 2560 × 1044，划为 3×2 栅格，单格约 853 × 522 |
| 最小触控热区 | **76 × 76px** |
| 最小字号 | **28px** |

> ⚠️ 若实车为 1920×720 横条屏，3×2 栅格与卡片比例需重做。**冻结前必须确认实际车型分辨率。**

### 7.3 Design Token

```
色彩（深色为主，夜间行车不刺眼）
  bg/base #0B0E14 · bg/surface #151A23 · bg/elevated #1E2530
  text/primary #F2F5FA · text/secondary #8A94A6
  brand #4DA3FF · success #3ED598 · warning #FFB84D · danger #FF5C5C
字阶（@2560）  display 72 / title 48 / body 32 / caption 28（下限）
圆角  sm 12 · md 20 · lg 32
动效  标准 240ms cubic-bezier(.4,0,.2,1)；入场 320ms / 出场 200ms
      物理动作（车窗/座椅/天窗）用真实时长，不加速
```

**`rejected` 用琥珀而非红色**：Agent 拒绝是正常的安全行为，不是错误。红色会让观众误以为系统出故障。

### 7.4 语音形象

**形态：抽象光球（方案 A）。** 理由不是省事——v1.0 要验证底层，形象越简单，观众注意力越容易集中在"AI 做对了什么"而非"卡通形象好不好看"。IP 形象 v0.3 再叠加。

**状态机（8 态）**

| 状态 | 形象 | 字幕 | 界面 |
|---|---|---|---|
| `idle` | 微弱呼吸，20% 亮度 | 无 | 常态 |
| `wakeup` | 200ms 放大 + 高亮 | "我在" | 卡片轻微让位 |
| `listening` | 波形随输入音量起伏 | **ASR 实时上屏** | 内容区降对比度 |
| `thinking` | 环形流动 | 省略号 | 无变化 |
| `speaking` | 随 TTS 节奏起伏 | **逐字上屏** | 无变化 |
| `executing` | **缩小 60% 移至角落** | 操作摘要 | **目标卡高亮描边 2s** |
| `confirming` | 高亮 + 脉冲 | 确认问句 | 确认卡浮起 |
| `rejected` | 变琥珀，短促收缩 | 原因 + 替代方案 | 相关卡闪烁琥珀 1 次 |

**两条硬规则**：

1. **executing 时形象必须让位**——Agent 不该挡住它正在操作的卡片。这一条直接决定 Demo 观感
2. **thinking 状态必须有**——真实大模型有 0.5~2s 首字延迟，没有 thinking 态用户会以为没听见

**待确认**：唤醒方式（唤醒词 / 按键 / 免唤醒），影响状态机入口。

### 8.1 首个 Demo：语音控制车窗

### 8.3 工程正确性保障

| 层 | 做法 |
|---|---|
| **状态不变量断言** | 运行时持续校验（§2.7），违反即在调试面板报警 |

## 附录 A · 行业对标结论摘要

详见《座舱Agent市场调研与设计对标_2026.08》。关键结论：

**我们对齐的（可放心继续）**

| 我们的设计 | 行业印证 |
