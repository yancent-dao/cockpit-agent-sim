# 座舱 Agent 模拟环境 · 需求规格说明书 v1.0

**文档状态**：v1.0 已实现并持续演进，本文保留作设计缘起存档——五条核心原则和行业定位判断至今没变，具体的接口细节以代码为准（工具清单见 [README](../README.md)，逐条设计决策见 `docs/superpowers/specs/`）。
**取代**：v0.1 接口定义、v0.2 分层修正与 UI 设计、v0.3 无 APP 化卡片桌面需求。
**日期**：2026-08-10（本次语言与内容校对：2026-08-19）

---

## 0. 摘要

### 0.1 要做什么

一套 Web 端的座舱底层软件模拟环境，为座舱 Agent 类 Demo 提供统一的车辆状态、能力接口、屏幕规范与演示控制，让每次做 Demo 不再从零开始、不再各行其是。

### 0.2 为什么值得做

- 从第 3 个 Demo 起，每个可省 60%~70% 重复工作
- 多个 Demo 共用底层后能拼成连贯的产品愿景，而非孤立的点
- 这套接口定义本身就是给研发的需求交付物，不是 Demo 的附属品
- Agent 座舱的产品定义 = 它的 Tool 集合，定义这套接口就是在定义产品

### 0.3 行业位置（详见附录 A，2026-08 时点）

- 车控 tool calling 在头部主机厂已是标配，不再是差异点；竞争焦点已转向长期记忆、任务规划、多 Agent 协同、跨场景连续性
- 全球不存在公开的「车载 Agent 能力描述规范」——这是真空，不是没找到
- 现成工具的分布：Kanzi/Qt/Unity 解决"HMI 长什么样"；RemotiveLabs+ProtoPie 解决"UI 接真实信号，但没有 Agent"；VehicleWorld/CAR-bench 有完整 Agent 工具语义但是没有 UI 的 Python CLI——中间那块没有产品
- 安全与授权机制是全行业公开空白（20+ 厂商中仅 Hyundai 公开命名 guardrail agent）——把确认与拒绝做扎实是领先，不是补课

### 0.4 核心设计原则（五条，贯穿全文，实现里也在用）

| # | 原则 |
|---|---|
| 1 | **Tools = 机制，Agent = 策略。** Tool 内不写任何"贴心逻辑"，所有意图理解与编排归 Agent |
| 2 | **平台不认识任何具体 Agent。** Agent 通过 Manifest 注册，新增 Agent 不改平台一行代码 |
| 3 | **不发明命名，不发明协议。** 信号对齐 VSS，元数据对齐 AAOS，确认流对齐 MCP MRTR |
| 4 | **拒绝必须携带机器可读原因。** Agent 的话术质量直接取决于拒绝信息的质量 |
| 5 | **无 APP 化下，"该执行什么"与"该显示什么"是两类决策**，必须分开建模 |

### 0.5 启动方式

寄生式演进：模拟环境永远挂在一个真实 Demo 需求上演进，不独立立项。验收标准不是"平台建好了"，而是"下一个 Demo 用它做出来了，且比不用更快"。

## 1. 架构分层

```
应用层 · Agent 实例（可插拔，平台不认识它们）
   主 Agent（agents/main-agent/）· 未来可加更多实例
Agent 编排层（平台提供，通用，不含任何具体 Agent 逻辑）
   快慢双层 pipeline · Scheduler 准入 · Turn 回合状态
   会话与多轮 · 并行编排 · 确认流(MRTR) · 可观测
能力层 Tools（src/tools/ + src/integrations/）
   L1 系统级：车控 · 卡片调度 · 语音
   L2 应用级：导航 · 媒体 · 天气 · 记忆 · 自动化任务 · 儿童绘本
状态层（src/core/ + src/state/）
   信号 Store · 约束引擎 · 长流程状态机 · 四级记忆
```

Agent 是一份 manifest（`agents/main-agent/manifest.ts`）+ 一段人设 Prompt + 一份技能包，不是代码。

### 1.1 L1 与 L2 的分界（产品意义大于技术意义）

| | L1 系统级 | L2 应用级 |
|---|---|---|
| 依赖 | 车自身硬件，一定存在 | 三方服务 / 网络 |
| 失败语义 | 车拒绝执行（有物理或安全原因） | 服务不可用（要有降级话术） |
| Agent 应对 | 解释原因 + 给替代方案 | 坦白 + 转移 |

Agent 面对两种失败的对话策略完全不同，这个差别演出来很有说服力。

### 1.2 分层是否成立的唯一验收标准

新建一个只挂 3 个 Tool、几十行人设的 Agent，不改平台任何一行代码就能跑起来。做不到，说明分层是假的。

## 2. 状态层

### 2.1 命名规范

双轨制：内部短别名用于 Prompt 注入（Token 效率），VSS 路径为必填字段（工程可交接）。构建期硬校验：没有合法 `vssPath` 的信号不允许注册。

> VSS v6.0 有破坏性变更（座椅信号重构、Left/Right → DriverSide/PassengerSide 等）。`src/config/signals.ts` 里的 `vssPath` 是待核验的推定路径，冻结前必须逐条对照官方 catalog。

其它命名约定：位置枚举全局唯一一套（`driver`/`passenger`/`rearLeft`/`rearRight`/`all`）；枚举值 lowerCamelCase；错误码 UPPER_SNAKE_CASE；百分比 0–100 整数。

### 2.2 信号元数据三元组（对齐 AAOS VehiclePropertyIds）

| 维度 | 取值 | 对 Agent 的意义 |
|---|---|---|
| **Access** | READ / WRITE / READ_WRITE | 决定是否生成 set 类 Tool |
| **ChangeMode** | STATIC / ONCHANGE / CONTINUOUS | 决定上下文注入策略：CONTINUOUS（车速）只注入摘要，STATIC 只注入一次 |
| **Permission** | 黑 / 灰 / 彩 | 见 §3.3 |

### 2.3 信号集

完整清单在 `src/config/signals.ts`（数据文件，直接读比看文档准）。覆盖行驶动力、热管理、车身开闭件、座椅个人化、灯光氛围、环境等域。加一个信号就是往这个文件加一行——不改任何平台代码。

### 2.4 约束与联锁

这些不是技术细节，是 Demo 的戏剧张力来源。约束引擎只支持 `[path, op, value]` 三元组（见 `src/config/constraints.ts`），复杂场景写具名谓词函数登记白名单——绝不引入表达式引擎或 `eval`。典型例子：行驶中限速开窗、儿童锁联锁、低电限功率、配置缺失。

### 2.5 过渡仿真（轻量，不做总线级）

明确不做 CAN 时延、信号丢失、报文级仿真。只做三件事让状态"像真车"：过渡时长可见可打断（车窗全程 4s 一类）、派生联动实时重算（续航随负载变化）、时间轴可加速。

### 2.6 状态不变量断言

运行时持续校验，违反即报警，例如：所有 position ∈ [0, 100]；儿童锁开启时后窗不发生变化。

## 3. 能力层（Tools）

### 3.1 统一返回契约

```ts
type ToolResult =
  | { status:'ok';            data?:object; changed?:string[]; code?:string; message?:string }
  | { status:'rejected';      code:string; message:string; suggestion?:string }
  | { status:'inputRequired'; code:'CONFIRM_REQUIRED'; message:string; token:string }   // MCP MRTR
  | { status:'unavailable';   code:string; message:string; suggestion?:string }
  | { status:'failed';        code:string; message:string }
```

| status | 含义 | Agent 应对 |
|---|---|---|
| `rejected` | 车能懂但不让做（安全/物理约束） | 解释原因 + 给替代方案 |
| `unavailable` | 车做不了（未选装/服务不可用） | 坦白 + 转移——这就是能力发现的失败转移，不是两套逻辑 |
| `failed` | 执行出错 | 致歉 + 建议重试 |
| `inputRequired` | 需二次确认 | 向用户确认后带 token 重调 |

`message` 必须写成人话，不是日志——它会直接进模型上下文。✅ `"当前车速 62km/h，行驶中无法开启车门"`　❌ `"ERR: door_open denied by speed guard"`

### 3.2 二次确认流程（对齐 MCP MRTR）

1. Agent 调用 `door.set({door:'trunk', action:'open'})`
2. Registry 拦截 → 返回 `{status:'inputRequired', message:'即将打开后备箱，确认吗？', token:'ct_a8f3'}`
3. 确认卡上屏，用户点确认/拒绝
4. 用户确认后，Agent 带 token 重新调用同一 Tool
5. Registry 校验 token（限时、一次性）后真正执行

由 Registry 拦截，不是靠 Agent 自觉。这把"哪些事 AI 能自作主张"变成了可配置参数——把某个 Tool 从彩改成灰，体验差异立刻可见。

### 3.3 权限分级（对齐行业「黑/灰/彩」）

| 级别 | 含义 | 判据 | 示例 |
|---|---|---|---|
| **彩** | Agent 可直接执行 | 可逆、无安全影响 | 调温、切歌、氛围灯 |
| **灰** | 需二次确认 | 不可逆 / 涉及安全 / 涉及金钱 / 涉及他人 | 开车门、存地址 |
| **黑** | 永久禁区，永不开放给 Agent | 直接影响行车安全 | 刹车、转向 |

「黑」= Tool 根本不注册给 Agent；`rejected` = Tool 存在但当前条件不满足。这是两件事，早期版本混淆过。

### 3.4 Tool 全集

完整清单见 [README「能力清单」](../README.md)，按域分组、带权限标注，声明在 `src/config/tools.ts` 里——加 Tool 就是往这个文件加一段数据，不用改平台代码。Tool 集完备性靠 VehicleWorld / VehicleMemBench / CAR-bench 交叉校验，缺什么补什么，多余的删。

### 3.5 每个 Tool 三张脸

一次定义，三处生成：代码 API（给平台调用）· Tool Schema（给 LLM 调用，自动导出多种格式）· 调试控件（给演示者在控制面板手动触发）。

## 4. 卡片桌面（无 APP 化）

### 4.1 前提与核心命题

无 APP 化改变了 Agent 的职责定义。有 App 的座舱里"显示什么"由 App 负责；无 APP 化把这份责任交还给 Agent。

Agent 面对两类决策：「该执行什么」和「该显示什么」，必须分开建模。执行对了但桌面一团糟，用户体感依然是失败。

### 4.2 栅格

主内容区 12×8（96 单元），14 种卡片形状，每个形状只允许一种几何——跨度取偶数、起点取偶数、最小 2×2，保证最小的卡永远填得上、不出现死缝。不追求空间利用率最优，追求演示者能预判结果。

> 最早的方案是 3×2（6 格，4 种形状），实现过程中经过 12×4 的中间阶段，最终定在 12×8——4 行时宽高比覆盖不全、中间档没有形状可选，8 行才补齐。尺寸自适应的设计过程见 `docs/superpowers/specs/2026-08-11-card-size-adaptive-design.md`。

### 4.3 卡片来源与生命周期

两条主线：**规则卡**（导航、车控回执这类，由声明式规则驱动，模型零参与）和**临场卡**（Agent 因一次意图建的候选列表、生成式小组件，走同一套布局仲裁）。放不下的卡进等位区排队，不会静默消失；有空位自动上台。设计过程见 `docs/superpowers/specs/2026-08-10-card-orchestration-design.md`、`2026-08-13-desk-offstage-design.md`。

### 4.4 卡片模板

模板契约三件套：数据形状（fields）· 形态（forms，按尺寸档变化）· 交互声明（interactions）。当前 22 个模板，声明在 `src/config/cards.ts`。两条硬纪律：相邻两档内容必须不同（同样的东西放大只会产生空白）；阅读方向决定长轴（列表用竖卡，对比用横卡）。

### 4.5 卡片实例必填字段

`ttl`（`untilDismissed` / 秒数 / `untilTaskEnd`，必须显式指定）、`kind`（决定抢占优先级基线）、`urgency`（正交于 kind，安全告警靠它压过来源身份）。

### 4.6 显示三通道

卡片放内容；横幅放解释（拒绝原因、执行回执——这些是对动作的说明，不是内容本身）；覆盖层留给危急告警与全屏内容。

### 4.7 反馈体系

优先复用桌面上已有的卡 → 其次放大 → 最后才新建。这既是防止卡片爆炸的工程规则，也是 Agent 编排能力的直接体现。

## 5. Agent 编排层

### 5.1 快慢双层（v1.0 时是接口预留，现已是核心实现）

一句话先到快层（小模型，只挂十几个可以放心先斩后奏的工具），能办的立刻办、立刻回话；无论办没办成都转交给慢层（大模型），两层共享同一份对话记录，慢层校验、接力、判断要不要补充话术。判断底层好坏的标准不是"Agent 表现好"，而是"Agent 表现差的时候，能一眼看出是模型的问题还是底层的问题"——这靠可观测面板保证。

### 5.2 上下文注入（每轮）

系统 Prompt 包含：角色人设、能力边界声明、车辆状态快照（按 ChangeMode 裁剪）、桌面布局摘要、环境快照、用户偏好（记忆系统注入）。状态直接注入而非让 Agent 调 `getState`，省掉一轮往返——座舱对首响延迟敏感。

### 5.3 记忆分四级

瞬时是信号 Store；会话是域仓结论加对话滑窗摘要；领域是播放队列、历史、收藏；长期是用户明说的偏好。偏好的自动学习不做——用户明说的记下来是数据，"连续三次调 24 度就记住"是策略，策略不进代码。

### 5.4 可观测面板

一屏展示：用户输入 → 注入的状态摘要 → 模型推理 → Tool 调用（名称/参数/权限级）→ 返回结果 → 卡片变化 → 最终话术 → 各段耗时。做成可投屏的独立窗口，评审时左边座舱界面、右边这个面板，"AI 到底做了什么"的黑盒感会消失。

### 5.5 自动化任务（原"主动式触发"，已实现）

用户用嘴建规则（"每天四点开空调""下雨自动关窗"），引擎常驻后台边沿触发，动作分两类：工具直调（零模型）、委托给慢层跑一句。替代传统情景模式，对标理想同类功能。

## 6. 能力发现（无 APP 化最大的产品风险）

双轨制：能力目录入口 + Agent 主动引导。

### 6.1 能力目录卡

硬性要求：由 Tool Registry 自动生成，不允许手写页面。能力增减自动同步，不会出现"目录里有但实际没有"；未选装能力自动置灰。

### 6.2 Agent 主动引导的三个时机

失败转移（能力不可用时给替代方案，跟 `unavailable` 的拒绝话术是同一件事）、对话顺带（任务完成后一句附加提示，需设频次上限）、场景触发（首次进入某场景时提示相关能力）。

## 7. 界面与交互规范

### 7.1 双界面架构

车机屏（投屏演示，纯净无调试元素：状态栏 + 卡片桌面 + 语音层）与控制面板（演示者操作：状态调节、模型选择、全链路日志），两者通过 BroadcastChannel 同步。

### 7.2 画布规范

基准屏 2560×1440（16:9），整屏等比缩放。`rejected` 用琥珀而非红色——Agent 拒绝是正常的安全行为，不是错误，红色会让观众误以为系统故障。

### 7.3 主题

日夜双配色，运行时可切（`theme.set`），夜间复用暗色语义 token 层；壁纸支持预设与 AI 生成，必带暗化/亮化遮罩保证卡片可读性。

### 7.4 语音形象（星河 Avatar）

顶栏角标 + 蒙层辉光的形态，八态参数纯函数驱动（`src/screen/galaxy.ts`）：待机、聆听、思考、播报、执行、确认、拒绝等状态各有对应的视觉与字幕节奏。两条硬规则：执行时形象要让位，不挡住正在操作的卡片；thinking 状态必须有，真实大模型有首字延迟，没有的话用户会以为没听见。触控交互（点屏幕）与语音并行，点星河图标 = 打断当前播报。

## 8. 工程验证

TDD 全程：先写测试看它红，再写实现看它绿，测试数量随功能持续增长，全绿才算完成。Tool 契约测试覆盖每个 Tool 的 `ok`/`rejected`/`unavailable` 路径，纯函数级、不依赖 LLM。

另有一套 pilot 自动化体验闭环：用独立的 LLM 扮演坐在车里的真人，跟真实 Agent 跑多轮对话，过程落盘成快照，人按产品设计、用户交互、架构、界面四个维度评审。很多真问题——几何死局导致导航卡出不来、思维链泄漏进播报、模型把轮次全烧在调工具上一句话没说——都是它抓出来的。

## 附录 A · 行业对标结论摘要（2026-08 时点）

详见《座舱 Agent 市场调研与设计对标》。关键结论：

**我们对齐的（可放心继续）**

| 我们的设计 | 行业印证 |
|---|---|
| L1/L2 原子能力与应用级能力分层 | 蔚来是唯一公开把「原子能力」写进架构的厂商 |
| Tools=机制 / Agent=策略 | 华为小艺定位「协调者而非全能体」；Qualcomm 把 MCP Server 定位为「模块化访问的抽象与控制点」 |
| Agent 从平台剥离、Manifest 注册 | 华为 HMAF 接入 50+ 三方 Agent；比亚迪演进为 Agent 生态平台 |
| 拒绝携带原因 + suggestion | Hyundai guardrail agent 是唯一公开对标，我们更细 |
| 说话人座位识别做指代消解 | Hyundai Gleo AI 明确公开此能力 |
| 可观测全链路面板 | 未见任何厂商公开做，属我们的差异化 |

**我们对齐的既有标准**

| 优先级 | 对象 | 对齐内容 |
|---|---|---|
| P0 | COVESA VSS v6.0 | 信号命名（vssPath 必填） |
| P0 | MCP | Tool schema 形态 + MRTR 确认流 |
| P0 | AAOS VehiclePropertyIds | Access + ChangeMode + Permission 三元组 |
| P1 | 火山引擎「黑/灰/彩」 | 权限分级表达 |
| P1 | VehicleWorld / VehicleMemBench | Tool 集完备性交叉校验 |
| P1 | CAR-bench | 任务类型学，用于评审维度设计 |
| P2 | A2A v1.0 | 架构预留，不实现（汽车业尚无采用） |
