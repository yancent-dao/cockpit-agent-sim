# 座舱 Agent 技术现状调研 与 我们的设计对标

> 调研时间：2026 年 8 月 · 覆盖 20+ 主机厂、7 个标准组织/协议、15 个现成工具与开源项目
> 目的：判断我们的模拟环境设计是否闭门造车，以及应当对齐什么

---

## 结论先行

**没有闭门造车，方向是对的，但有 6 处必须修正。**

三句话概括：

1. **我们做的分层（原子能力 / 应用级能力 / 主 Agent 编排）与行业头部收敛的结论一致**——蔚来、华为、大众 CEA 2.0 都走到了「总调度 Agent + 垂域执行 Agent」这个结构上。
2. **我们最该改的是"自己发明命名和协议"这件事。** 行业已经有 VSS v6.0（信号词汇表）和 MCP（工具协议）两套既成事实，上一版我判断"VSS 全路径太长不用"是错的，得改。
3. **我们最有价值的部分恰恰是全球空白**：截至 2026 年 8 月，**不存在任何一份公开的「车载 Agent 能力描述规范」**，也不存在任何一个「产品经理可用的座舱 Agent 原型工具」。这不是我们没找到，是真空。

## 第一部分 · 行业现状速览

### 1.1 主机厂：车控 tool calling 已是标配，不再是差异点

| 已具备车控执行能力 | 仍停留在对话/推荐 |
|---|---|
| 蔚来、华为/问界、理想、小鹏、极氪、智己、比亚迪、小米、长城、吉利<br>Tesla（2026-07 开放硬件控制）、BMW（Alexa+）、Hyundai、Rivian、GM/Gemini | Mercedes（Gemini 对话式搜索，未公开车控）<br>Stellantis（定位交互式用户手册）<br>Toyota（未查到量产 LLM Agent） |

**这条对你很重要**：如果你的 Demo 只演"语音能开窗"，2026 年已经不构成亮点。行业共识是竞争焦点已从「有没有大模型」转到「能不能办成事」，决定质量的四项是**长期记忆、任务规划、多 Agent 协同、跨场景连续性**——都不是模型参数量。

### 1.2 五个行业共性趋势

| 趋势 | 代表 |
|---|---|
| **端云混合 + 快慢思考** 成为主流工程范式 | 华为 MoLA 2.0（快/慢思考双模）、比亚迪迪迪虾（端云协同+快慢思考）、Hyundai（端侧跑安全关键车控 / 云端跑复杂计算）、小鹏（7B VLM 全端侧） |
| **多 Agent 分层：总调度 + 垂域执行** | 华为 System Agent + 导航/控车/聊天 Agent；蔚来 认知中枢 + 知识/生成/任务三类 Agent；大众 CEA 2.0（2027 统一多 Agent） |
| **座舱与智驾模型合流，"整车智能体"取代"座舱助手"** | 极氪超级 Eva（座舱可下发智驾+底盘+动力）、智己 IM Fusion Nova、小鹏 VLM×VLA |
| **主动服务开始可分级** | 长城「相识 → 相知 → 相助」三级；华为「从类平板走向 AI 主动服务」 |
| **安全与授权机制是全行业公开空白** | 20+ 厂商中，只有 Hyundai 公开命名 **guardrail agent**（执行前拦截危险请求）、小米有可见的用户授权开关、大众公开了能力边界隔离。**二次确认机制几乎无人公开描述，包括已开放硬件控制权的 Tesla** |

> 最后一条是好消息：**我们把确认与拒绝机制做扎实，是行业领先而非补课。**

### 1.3 值得单独注意的三家

- **蔚来**：业界唯一公开把「**原子能力**」写进架构底层的厂商，且 Agent 按「知识类/生成类/任务类」而非功能域切分。你的 L1/L2 分层与它同源。
- **华为 HarmonySpace 6**（2026-04）：宣称「业界首个智能座舱开放 AI Agent 生态」，有统一的三方 Agent 接入标准，接入 50+ 专家 Agent，小艺定位为**协调者而非全能体**，支持 A2A 跨域调用。**且鸿蒙座舱模拟器已上线 DevEco Studio。** 如果你们在鸿蒙智行体系内，这是要对齐而非自建的对象。
- **火山引擎豆包座舱**：车控权限分 **黑 / 灰 / 彩三层**，刹车转向为 AI 禁区。豆包已上车 700 万+ 辆、145 款车型。这个分级说法是中国市场的事实共识。

### 1.4 标准与协议：两套必须对齐，一套可以缓

| 标准 | 现状 | 对我们的意义 |
|---|---|---|
| **COVESA VSS v6.0**（2026-01 发布） | 唯一被 OEM/Tier1/AGL/Kuksa 共同接受的车辆信号词汇表。BMW 在 2026 春季 COVESA 大会贡献了 **VSS-for-VHAL**（VSS↔Android VHAL 映射）；日本 JASPAR 2026-04 开源 **Yoriito**（1000+ API，建在 VSS/VISS 之上） | **P0 必须对齐**。这是我上一版判断失误的地方 |
| **MCP（2026-07-28 规范）** | 重构为无状态请求/响应，新增 **MRTR（Multi Round-Trip Requests）支持调用中途确认**。**Qualcomm 官方 Agentic AI 白皮书已按域给出 ADAS / Cockpit / TCU / V2X MCP Server 架构**；mimik 把 MCP Gateway 带入 SOAFEE Blueprint | **P0 必须对齐**。尤其 MRTR 天然就是"要不要帮你开天窗？"这类车内确认对话 |
| **AAOS VehiclePropertyIds** | 300+ 属性，每个带 **Access + ChangeMode + Permission** 三元组元数据 | **P0 对齐元数据模型**（不是对齐 API） |
| **A2A v1.0**（2026-04 Linux Foundation） | 150+ 组织支持，但**点名成员全是 IT 阵营，无一家车企/Tier1** | P2，架构图上预留即可，不实现 |
| **AUTOSAR / CCC** | 未查到任何 AI Agent 相关工作 | 不相关 |
| **中国团体标准** | 现有 T/CSAE 322-2023、T/CAAMTB 151-2023 均为座舱智能化评价；2026 年《汽车智能座舱团体标准体系研究报告》**自己承认**「座舱专属 AI 应用、大模型集成标准、场景测评体系仍存在空白」 | 无可对齐对象 |

**关键判断：全球范围内不存在一份公开的「车载 Agent 工具/能力描述」标准。** MCP 官方 registry 里搜 "vehicle" 只有 VIN 解码、召回查询这类**车外数据**服务，**没有一个是车内功能控制**。

### 1.5 现成工具：有三个半轮子，但没有一个能直接用

| 项目 | 是什么 | 判断 |
|---|---|---|
| **Eclipse autowrx / digital.auto playground** ⭐ | **浏览器里的 SDV 原型环境**：VSS API 目录 + 3D 车模映射 + 门/座椅/灯光 widget 库 + 测试 Dashboard，MIT 协议，最新 v2026.06.30 | **和我们要做的东西最接近，必须先跑一遍。但它只跑 Python 脚本，没有 LLM / tool calling / 对话** |
| **Eclipse Kuksa databroker** v0.7.0 | VSS 状态中枢（gRPC+VISS）+ kuksa-mock-provider 信号模拟 | **可直接用作状态层**，Docker 一行起 |
| **VehicleWorld**（OpenMOSS, EMNLP 2025） | **首个综合性座舱 Agent 交互环境**：30 模块 / 250 API / 680 属性 | **必须读它的 API schema 设计** |
| **CAR-bench**（ACL 2026, MIT 协议） | 车内助手基准：58 个互联 tools、19 条领域策略、254 任务，含**幻觉任务**与**歧义消解任务** | **它的任务类型学直接就是我们的 Golden Case 分类法** |
| **VehicleMemBench** | 111 个可执行 API 分 23 类设备 | Tool 清单交叉校验 |
| **MCP-CAN** | 唯一开源的「车辆 MCP Server」（虚拟 CAN + ECU 仿真 + OBD 诊断） | 诊断域不是座舱域，参考实现形态 |
| **RemotiveLabs + ProtoPie + Figma** | PM/设计师最现实的既有组合：Figma 出图 → ProtoPie → 接真实车辆信号（VSS 命名） | 有 UI 有真数据，**但没有 Agent / tool calling 那一层** |
| Kanzi / CGI Studio / Qt / Unity | 量产 HMI 交付工具 | 解决"HMI 长什么样"，不解决"Agent 该有哪些能力" |

**最关键的一条发现**：`digital.auto` 有 Web 前端 + VSS 但没有 Agent；`VehicleWorld / CAR-bench` 有完整 Agent 工具语义但是**给研究者跑评测的 Python CLI，没有 UI**。**这两半之间没有人接上——那就是我们的位置。**

### ⚠️ 必须修正的 6 条

#### 修正 1 · VSS 从"可选参考"升为"必填映射"（P0）

**上一版我错了。** 我以"VSS 全路径太长、吃 Token、降低模型可读性"为由把 `vssRef` 列为可选。但调研显示 VSS v6.0 是 OEM/Tier1/AGL/Kuksa/JASPAR/BMW 共同接受的唯一词汇表，不对齐等于你的 Demo 无法被工程团队接手。

**修正方案（两全）**：

```yaml
- alias:   cabin.window.driver.position     # 内部短别名，注入 Prompt 用（Token 效率是真的）
  vssPath: Vehicle.Cabin.Door.Row1.DriverSide.Window.Position   # 必填，不可省
  access:  READ_WRITE          # ← 修正 2
  changeMode: ONCHANGE         # ← 修正 2
  permission: 彩               # ← 修正 4
```

别名保留，但 **vssPath 升为必填字段，并加一条构建期校验：任何没有合法 vssPath 的信号不允许注册。**

#### 修正 2 · 信号元数据补齐 AAOS 三元组（P0）

我上一版只有 RO/RW，缺两个维度。AAOS `VehiclePropertyIds` 的三元组正是 Agent 需要的：

| 维度 | 取值 | 对 Agent 的意义 |
|---|---|---|
| **Access** | READ / WRITE / READ_WRITE | 决定是否生成 set 类 Tool |
| **ChangeMode** | STATIC / ONCHANGE / CONTINUOUS | **决定要不要注入 system prompt、要不要订阅**。CONTINUOUS（如车速）不能每次全量注入，只注入摘要 |
| **Permission** | 权限等级 | 见修正 4 |

> ChangeMode 这一维我原来完全没有，但它直接决定上下文注入策略，属于漏了的关键设计。

#### 修正 3 · 二次确认改为对齐 MCP MRTR，不要自造 confirmToken（P0）

我上一版自己发明了 `needsConfirmation + confirmToken` 流程。MCP 2026-07-28 规范新增的 **MRTR（Multi Round-Trip Requests）** 就是干这个的，形态为 `resultType: "input_required"`。

**修正**：语义保持不变（Runtime 拦截 → 返回需确认 → Agent 问 → 带凭证重调），但**字段名和返回结构改为 MCP MRTR 形态**。这样未来把我们的 Tool 层直接暴露成一个 Cockpit MCP Server 时，零改造。

考虑到 Qualcomm 已在官方架构里画了 **Cockpit MCP Server**，这个对齐的战略价值很高。

#### 修正 4 · 权限分级改用行业「黑 / 灰 / 彩」说法（P1）

我的 `auto / confirm / blocked` 三级正好对应火山引擎的三层，但行业用的是后者的说法。**语义不变，改称呼**，好处是内部沟通和对外汇报时不用解释：

| 我们原来 | 改为 | 含义 |
|---|---|---|
| `auto` | **彩** | Agent 可直接执行（调温、切歌、氛围灯） |
| `confirm` | **灰** | 需二次确认（开门、行驶中开窗、支付、发消息给他人） |
| `blocked` | **黑** | AI 禁区，永不开放（刹车、转向） |

> 注意：我原来的 `blocked` 语义是"当前状态下不可用"，这和行业「黑」（永久禁区）不是一回事。**要拆成两个**：`黑`=永久禁区，`rejected`=当前条件不满足。这是个真实的语义 bug。

#### 修正 5 · Golden Case 升级为 CAR-bench 三类任务学（P0）

CAR-bench 的核心发现值得单独说：

> **前沿模型呈现 "Completion > Compliance"——宁可编造工具输出，也不愿承认能力缺失。**

这条直接证明我的 Golden Case #7（未选装天窗不幻觉）不是锦上添花，而是**必测项**，而且 6 条正常路径 + 1 条反幻觉的配比太低了。

**修正**：Golden Case 按 CAR-bench 分三类，并提高边界类占比：

| 类别 | 原配比 | 修正后 | 说明 |
|---|---|---|---|
| **Base** 正常路径 | 4 条 | 3 条 | 验证链路成立即可 |
| **Disambiguation** 歧义消解 | 3 条 | 3 条 | 上下文、说话人、打断 |
| **Guardrail** 边界与拒绝 | 2 条 | **3 条起，v0.2 扩到 8 条** | 反幻觉、约束拒绝、能力缺失 |

（新的双界面 Demo 里已经按这个分类重排了）

#### 修正 6 · 补上"快慢思考 / 端云混合"的架构预留（P1）

这是行业主流工程范式（华为、比亚迪、Hyundai 在不同市场独立收敛到同一结论），我上一版完全没提。

**修正**：Agent Runtime 增加一个 `thinkingMode` 维度：

- `fast`：明确指令直通，跳过深度推理（"开窗" → 直接 tool call）
- `slow`：开放性问题走完整推理，UI 显示"思考中"

v0.1 不必实现两套模型，但**接口和 UI 状态要留出来**——`thinking` 状态在我们的语音形象状态机里已经有了，正好对上。

### 📌 需要你决策的 2 个战略问题

**1. 要不要 fork Eclipse autowrx？**

它是 MIT 协议、Web 前端、自带 VSS API 目录和 3D 车模 widget 库。自建 UI 骨架大概要花 2~3 周，fork 它可能 3 天。代价是要读懂一套陌生的 React 代码，且它的架构是围绕"跑 Python 脚本"设计的，接 Agent 要改不少。

> 我的建议：**先花半天跑一遍 digital.auto playground 再决定**。如果它的 widget 和 Dashboard 结构可用，就 fork 骨架、自建 Agent 层；如果耦合太深，就只抄它的 VSS API 目录组织方式。

**2. 你们是否在鸿蒙智行体系内？**

华为 HarmonySpace 6 已宣称推出「业界首个智能座舱开放 AI Agent 生态」并有统一三方 Agent 接入标准，且**鸿蒙座舱模拟器已上线 DevEco Studio**。如果你们的车型走鸿蒙座舱，那正确动作是对齐它的接入标准而不是自建一套；如果是自研座舱，自建成立。

## 第三部分 · 我们真正的空白价值

调研下来，我们要做的东西可以精确定义为三件，其中第一件全球不存在：

### 1. 一份 VSS 对齐的「座舱 Agent 能力清单」

字段 = `VSS 路径 + Access + ChangeMode + 权限等级（黑/灰/彩） + MCP Tool Schema + 拒绝码与话术`

**这个东西目前世界上不存在。** Qualcomm 只在白皮书里画了 Cockpit MCP Server 的框，mimik 只提出了分层原则，COVESA 的 MCP 工作在研发工具链而非车内，中国团标自己承认这块空白。

对你个人而言，这份清单不是"Demo 的配套物"，**它本身就是可以拿去做行业交流、给研发交付、甚至推动内部标准的产出**。

### 2. 一个 PM 可用的 Web 端座舱 Agent 原型环境

现有工具的分布是：
- 解决"HMI 长什么样"：Kanzi / CGI Studio / Qt / Unity（量产交付工具，PM 用不了）
- 解决"UI 接真实信号"：RemotiveLabs + ProtoPie + Figma（有 UI 有数据，**没有 Agent**）
- 解决"Agent 工具语义"：VehicleWorld / CAR-bench（**Python CLI，没有 UI**）

**中间那块，没有产品。**

### 3. 一套失败场景剧本

直接移植 CAR-bench 的 Hallucination / Disambiguation 任务类型。这是把 Demo 从"演示 PPT"变成"决策依据"的关键——**因为行业已经证明了模型会编造工具输出，而没有一家厂商公开了他们的应对机制。**
