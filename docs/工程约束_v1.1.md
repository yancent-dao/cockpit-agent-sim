# v1.1 · 工程约束与技术选型

> 本文是 v1.0 需求规格说明书的补充，不改动需求，只约束实现方式。
> 原定日期：2026-08-10。本次校对（2026-08-19）把技术选型段落改成了实际落地的选择——
> 原计划的 Vue/YAML 配置在实现时换成了零框架 TypeScript，其它约束条款没变，
> 具体数字与目录结构以当前代码库为准。

---

## 0. 先把"简洁"翻译成可执行的东西

"保持简洁"如果只是原则，三个月后一定会被违反。所以本文把它拆成四条可检查的约束：

| # | 约束 | 检查方式 |
|---|---|---|
| 1 | **零后端** | 产物是一组静态文件，双击即可打开 |
| 2 | **加能力 = 加数据，不加代码** | 新增一个信号 / 约束 / Tool，若需要改 core 代码即视为设计失败 |
| 3 | **复杂度只允许落在几个已知位置**，且各有上限 | 见 §3 |
| 4 | **代码里不允许出现意图分支** | 出现 `if (intent === ...)` / `if (userSaid.includes(...))` 即违规 |

第 4 条是 v1.0 第一原则「Tools=机制 / Agent=策略」的可执行版本。它是这套系统会不会腐烂的分水岭——一旦代码开始猜用户想干什么，分层就名存实亡了。

## 1. 技术选型（实际落地）

### 1.1 决策与理由

| 项 | 决策 | 理由 |
|---|---|---|
| 后端 | **无** | LLM API 从前端直连，Key 存本地 `.env.local`（不入库、不提交） |
| 构建 | **Vite** | 零配置、启动快、原生支持 TS |
| 框架 | **无**，纯 TypeScript + 手写 DOM 操作 | 界面结构不复杂到需要框架的地步；引入框架本身就违反"运行时依赖为零" |
| 语言 | **TypeScript** | 接口契约是本项目的核心产物，类型能防止契约漂移 |
| 状态管理 | **不引入任何库** | Store（`src/core/store.ts`）本身就是状态管理，再套一层是重复 |
| 样式 | **原生 CSS + CSS 变量** | Design Token 就是 CSS 变量，不需要 Tailwind |
| 配置数据 | **TypeScript 常量文件**（非 YAML） | 跟业务代码同一个类型系统检查，少一层解析和一类运行时错误 |
| 存储 | **内存 Store + localStorage**（域仓/偏好） | 不用数据库 |
| 测试 | **Vitest** | 覆盖 `core`/`tools`/`integrations`/`agent`/`cards`/`screen` 的纯函数与契约，UI 渲染不做像素级单测 |

### 1.2 依赖预算（已达成）

**运行时 devDependency 只有 3 个**：`vite`、`vitest`、`typescript`。唯一例外是导航卡接高德地图 JS SDK——运行时 `<script>` 动态加载，不进 `package.json`，这是产品明确接受的一次性代价，不代表这条约束松动。

任何新增依赖需要回答一句话：**"不加它要多写多少行？"** 少于 200 行就自己写。

### 1.3 明确不引入（附理由）

| 不引入 | 理由 |
|---|---|
| Eclipse autowrx（不 fork） | 全栈架构围绕"浏览器跑 Python 脚本"，接 Agent 改动量大于自建，且破坏零后端 |
| Eclipse Kuksa databroker | Rust + gRPC + Docker，对纯前端 Demo 是净负担 |
| Tailwind / UI 组件库 | 座舱视觉是定制的，组件库反而要覆盖 |
| 状态管理库 / 路由库 | 单页单屏，用不上 |
| 3D 引擎 | 车辆用 SVG 二维示意足够，且更清晰 |

### 1.4 「对齐而不引入」策略

不用它们的代码，但要用它们的语义——这样简洁性和可交接性能同时保住：

| 对象 | 引入形态 | 代价 |
|---|---|---|
| **VSS v6.0** | 只作为 `vssPath` 字段值 + 构建期校验 | 几乎为零 |
| **Kuksa** | Store 的 `get`/`set`/`subscribe` 方法签名照抄它的语义 | 零，将来接真车换一个 adapter 即可 |
| **MCP MRTR** | 返回契约用 `inputRequired` 形态 | 零 |
| **AAOS** | 信号元数据三元组的字段名与取值 | 零 |

## 2. 数据驱动：加能力 = 加数据

这是简洁性最大的杠杆。代码只写解释器，能力全部用数据描述——落地在 `src/config/`：

```
src/config/
├── signals.ts       # 信号定义（VSS 对齐）
├── constraints.ts   # 约束三元组
├── tools.ts         # Tool 契约
├── cards.ts         # 卡片模板
├── cardRules.ts     # 桌面声明式规则
├── priority.ts       # 抢占优先级权重表
└── upstream.ts       # 三方服务地址表（同源代理用）
```

**signals.ts**

```ts
{ alias: 'cabin.window.driver.position',
  vssPath: 'Vehicle.Cabin.Door.Row1.DriverSide.Window.Position',
  type: 'number', range: [0, 100],
  access: 'READ_WRITE', changeMode: 'ONCHANGE',
  permission: '彩', transition: 4000, initial: 0 }
```

**constraints.ts** —— 表达式故意限定为三元组，不支持嵌套逻辑：

```ts
{ id: 'SPEED_LIMITED', when: ['vehicle.speed', '>', 100],
  target: 'cabin.window.*.position', action: 'clamp', value: 30,
  message: '当前车速 {vehicle.speed}km/h，车窗最多开到 {value}%' }
```

> 三元组覆盖绝大多数约束场景，剩下的用具名谓词函数（见 §3.1），绝不引入表达式引擎或 `eval`。

**tools.ts** —— 每个 Tool 声明 name/brief/desc/permission/params/handler；纯业务判断少的 Tool，handler 也会很薄。

### 2.1 由数据自动派生的东西

一处定义、多处生成：`tools.ts` → Tool Schema（OpenAI 格式，供快慢两层的 LLM 调用）、调试面板控件（控制面板里的按钮自动长出来）、能力目录卡内容。

## 3. 复杂度的几个落点与上限

复杂性不会消失，只会转移。与其让它到处渗，不如指定几个落点并各设上限——完整的目录级预算记账（哪些超了、为什么超、超了要不要拆）在 `CLAUDE.md`（本地文件，不进版本库），这里只记原则：

### 3.1 约束引擎

只支持 `[path, op, value]` 三元组，op 限 `> < >= <= == !=`。超出的场景写成具名谓词函数，登记在白名单里，按名字引用。禁止 `eval`、表达式解析库、嵌套 and/or。

### 3.2 卡片布局

12×8 栅格，14 种形状，每个形状只允许一种几何——布局问题从二维装箱降为一维排布。不追求最优解，追求可预测解：演示者能预判结果比空间利用率重要。满载策略：降尺寸 → 挤出低优先级卡 → 进等位区排队 → 告知用户，静默消失不可接受。

### 3.3 Agent 编排

全部在 Prompt 里，代码零意图分支。代码只做四件事：上下文拼装 · 并行调用 · 结果回填 · 确认流转。违规信号：代码里出现 `if (intent===...)`、关键词匹配、意图枚举。

> 这条最容易被破坏。当 Agent 表现不好时，最大的诱惑就是"在代码里兜一下"。兜了就等于把说服力抽掉了——观众会分不清是模型聪明还是代码作弊。正确做法是改 Prompt 或改 Tool 描述。

---

## 4. 代码规模预算

按目录设预算，超了不是提高预算，是先查有没有业务逻辑漏进了不该在的层——尤其检查 UI 里有没有藏业务规则。三个复杂度落点（约束引擎、卡片布局、Agent 编排）各自的实际行数记账见 `CLAUDE.md`。`src/config/*.ts`（数据）与 `src/screen/`、`src/director/`（UI，天然啰嗦但不许有业务逻辑）不设硬预算。

---

## 5. 明确不做（简洁性靠"不做"保证）

| 不做 | 何时再议 |
|---|---|
| 后端服务、数据库、用户系统 | 永不 |
| 多屏（仪表 / HUD / 副驾 / 后排） | 第二块屏有真实需求时，届时抽 `ScreenProfile` |
| 完整设计系统、表单体系、国际化 | 永不 |
| Tool 路由 / 分级检索 | 实测到模型选错或明显变慢时——当前全量挂载 |
| 真实 ASR（用文本输入模拟） | 有真实需求时 |
| 多 Agent 实现（只留接口） | 有第二个 Agent 的真实需求时 |
| CAN 时延 / 丢包 / 报文级仿真 | 永不 |
| 接真车 / Kuksa / VISS | 有落地需求时，换 adapter |
| 偏好自动学习 | 永不——自动学习是策略，策略不进代码 |

## 6. 目录结构（扁平优先，实际落地）

```
cockpit-sim/
├── src/
│   ├── config/        # 信号 · 约束 · Tool · 卡片模板 · 桌面规则（数据）
│   ├── core/           # Store · 约束引擎 · 长流程状态机 · 自动化引擎
│   ├── tools/          # 注册表：授权 · 契约 · MRTR
│   ├── integrations/   # 三方协议客户端 + handler（业务逻辑在这层）
│   ├── agent/           # 快慢双层 pipeline · Scheduler · Turn · LLM 适配
│   ├── cards/           # 卡片桌面：栅格仲裁 · 生命周期 · 等位区 · 重力
│   ├── state/            # 记忆：域仓 · 偏好 · 会话摘要 · 绘本
│   ├── screen/          # 车机屏（纯净可投屏，禁业务逻辑）
│   ├── director/        # 控制面板（调试/演示，禁业务逻辑）
│   └── design/           # Design Token
├── agents/
│   └── main-agent/      # manifest + 人设 + 快层微人设 + 技能包
├── tests/               # 与 src/ 同构，模块对模块
└── docs/                 # 需求、约束、逐轮设计文档
```

**不做 monorepo。** 单包单 `package.json`，`src/` 下按目录分层即可。monorepo 的收益要到多包复用时才出现，现在只会增加配置负担。

## 7. 三条会在实现期反复用到的判断准则

1. **要不要抽象？** —— 出现第二次重复才抽。第一次直接写。
2. **要不要配置项？** —— 演示时会当场改的才做成配置，否则写死。
3. **要不要兜底？** —— 兜到 Tool 层为止；Agent 表现不好改 Prompt，不改代码。
